Koyeb and W7S both target teams that want to deploy software without managing a traditional platform stack, but they start from different assumptions.

Koyeb is a global serverless infrastructure platform for APIs, inference, applications, and databases. Its public site emphasizes deploying intensive workloads across GPUs, CPUs, and accelerators in many locations, with a strong focus on AI infrastructure.

W7S is a GitHub-native deployment platform for repository-shaped apps. It is designed for static frontends, JavaScript and TypeScript backends, storage bindings, queues, schedules, workflows, internal RPC, and branch environments deployed from GitHub Actions.

The short version:

> Choose Koyeb when the workload is infrastructure-shaped. Choose W7S when the product should deploy from GitHub as an app-shaped repository with built-in platform primitives.

## Koyeb vs W7S

| Question | Koyeb | W7S |
| --- | --- | --- |
| What is it? | Serverless infrastructure for APIs, inference, applications, databases, and AI workloads | GitHub-native app deployment platform |
| Main unit | Service, workload, or infrastructure deployment | GitHub owner, repository, branch, and environment |
| Strongest fit | APIs, containers, AI inference, GPU or accelerator workloads, global infrastructure | Static apps, native backends, repo-declared resources, queues, schedules, workflows |
| Deployment style | Platform deployment from Git, container, or infrastructure workflow | GitHub Actions workflow using `w7s-io/w7s-cloud@v1` |
| Runtime model | General service infrastructure with CPU, GPU, and accelerator options | Narrow app runtime with frontend assets and native backend primitives |
| Operations goal | Scale infrastructure in managed global regions | Remove infrastructure decisions from repo-shaped apps |
| Main tradeoff | More infrastructure choices to understand | Less flexible than a general service or container platform |

## What Koyeb Is Best At

Koyeb is strongest when the app starts as a service or workload that needs infrastructure choices.

Use Koyeb when you care about:

- deploying APIs or services globally;
- running containerized workloads;
- deploying AI inference workloads;
- using GPUs, CPUs, or accelerators;
- scaling services across many locations;
- keeping a serverless infrastructure model without managing your own cluster.

That is a good fit for teams that want managed infrastructure but still need to think in services, regions, machine classes, and workload profiles.

## What W7S Is Best At

W7S is strongest when the app starts as a repository.

A W7S app can declare its deployment workflow in GitHub:

```yaml title=".github/workflows/deploy.yml"
name: Deploy

on:
  push:
    branches: [main]

permissions:
  id-token: write
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: w7s-io/w7s-cloud@v1
```

The repository can also declare runtime resources:

```json title="w7s.json"
{
  "bindings": {
    "db": [
      {
        "binding": "DB",
        "migrations": "migrations"
      }
    ],
    "kv": ["CACHE"]
  },
  "queues": ["jobs"],
  "schedules": [
    {
      "cron": "0 * * * *",
      "path": "/_w7s/schedules/hourly"
    }
  ]
}
```

Use W7S when you want:

- GitHub Actions to be the deployment control plane;
- static frontend and backend routes deployed together;
- branch previews tied to Git branches;
- app resources declared beside code;
- backend queues, schedules, workflows, and RPC without a separate service topology;
- a deploy path that is easy to copy across small and medium apps.

## Where Koyeb Wins

Koyeb is a better fit when the workload needs a broader infrastructure surface.

Choose Koyeb for:

- AI inference that needs GPU or accelerator choices;
- container-first workloads;
- services that need more runtime flexibility than W7S native backends;
- teams that want a managed global infrastructure platform;
- apps where infrastructure shape matters more than repository simplicity.

Koyeb is not just a website host. It is closer to a serverless infrastructure layer for modern workloads.

## Where W7S Wins

W7S is a better fit when the app should stay simple and repo-native.

Choose W7S for:

- marketing sites that grow into real apps;
- JavaScript and TypeScript backend routes;
- webhook handlers;
- dashboards;
- scheduled jobs;
- queue consumers;
- small SaaS backends;
- internal tools;
- apps where GitHub should remain the source of deployment truth.

The W7S bet is that many apps do not need to choose machines, regions, service classes, or container topology. They need a repository, a deploy action, and platform primitives that behave like code.

## Recommendation

Use Koyeb if your next problem is infrastructure: AI workloads, global services, containers, GPUs, accelerators, or service scaling.

Use W7S if your next problem is app delivery: take a repository, deploy it from GitHub, attach storage and backend primitives, and keep the operational surface small.

They are both useful. The difference is where you want the product boundary to live: at the infrastructure service layer, or at the GitHub repository layer.
